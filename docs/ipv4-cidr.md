# IPv4와 CIDR 이해하기

이 문서는 IPv4 주소와 CIDR(Classless Inter-Domain Routing)의 기본 개념을 정리하고, 이 프로젝트의 AWS 네트워크 설정에 각 표기가 어떻게 사용되는지 설명한다.

## IPv4 주소

IPv4 주소는 네트워크에 연결된 장치를 식별하는 32비트 주소다. 사람이 읽기 쉽도록 8비트씩 네 부분으로 나누고, 각 부분을 10진수로 표현한다. 각 부분을 **옥텟(octet)**이라고 하며 `0`부터 `255`까지의 값을 가질 수 있다.

```text
10.0.1.25

10       .0        .1        .25
00001010.00000000.00000001.00011001
```

IPv4 주소는 네트워크를 나타내는 부분과 그 네트워크 안의 장치를 나타내는 호스트 부분으로 구성된다. 두 부분의 경계는 서브넷 마스크 또는 CIDR 접두사 길이로 구분한다.

## 공인 IPv4와 사설 IPv4

공인 IPv4 주소는 인터넷에서 고유하며 인터넷을 통해 직접 라우팅할 수 있다. 사설 IPv4 주소는 내부 네트워크에서 사용하며 인터넷에서는 직접 라우팅되지 않는다.

사설 IPv4 주소 범위는 다음과 같다.

| CIDR | 주소 범위 | 전체 주소 수 |
|------|-----------|-------------:|
| `10.0.0.0/8` | `10.0.0.0` ~ `10.255.255.255` | 16,777,216 |
| `172.16.0.0/12` | `172.16.0.0` ~ `172.31.255.255` | 1,048,576 |
| `192.168.0.0/16` | `192.168.0.0` ~ `192.168.255.255` | 65,536 |

이 프로젝트의 VPC와 Subnet은 사설 주소 대역인 `10.0.0.0/8` 안에서 각각 `10.0.0.0/16`과 `10.0.1.0/24`를 사용한다. EC2가 인터넷과 직접 통신하려면 사설 주소만으로는 부족하며, Public IPv4 또는 Elastic IP와 Internet Gateway를 통한 경로가 필요하다.

## 서브넷 마스크와 CIDR

서브넷 마스크는 IPv4 주소에서 네트워크 부분과 호스트 부분을 구분한다. CIDR은 이를 `/접두사 길이` 형태로 간결하게 표현한다. 접두사 길이는 32비트 중 네트워크 부분으로 사용하는 비트 수다.

예를 들어 `/24`는 앞의 24비트가 네트워크 부분이고, 나머지 8비트가 호스트 부분이라는 뜻이다.

```text
CIDR:         10.0.1.0/24
서브넷 마스크: 255.255.255.0

네트워크 부분: 11111111.11111111.11111111.00000000
호스트 부분:                                      8비트
```

접두사 길이가 클수록 네트워크 범위는 작아지고, 접두사 길이가 작을수록 범위는 커진다.

| CIDR 접두사 | 서브넷 마스크 | 전체 주소 수 | 일반적인 의미 |
|-------------|---------------|-------------:|---------------|
| `/0` | `0.0.0.0` | 4,294,967,296 | 모든 IPv4 주소 |
| `/8` | `255.0.0.0` | 16,777,216 | 매우 큰 네트워크 |
| `/16` | `255.255.0.0` | 65,536 | 이 프로젝트의 VPC 범위 |
| `/24` | `255.255.255.0` | 256 | 이 프로젝트의 Public Subnet 범위 |
| `/32` | `255.255.255.255` | 1 | 단일 IPv4 주소 |

전체 주소 수는 호스트 부분의 비트 수를 이용해 다음과 같이 계산한다.

```text
전체 주소 수 = 2^(32 - CIDR 접두사 길이)
```

따라서 `/24`에는 `2^(32 - 24) = 256`개의 주소가 포함되고, `/16`에는 `2^(32 - 16) = 65,536`개의 주소가 포함된다.

## 네트워크 주소와 브로드캐스트 주소

일반적인 IPv4 서브넷에서는 호스트 부분이 모두 `0`인 첫 번째 주소를 **네트워크 주소**, 모두 `1`인 마지막 주소를 **브로드캐스트 주소**로 사용한다.

`10.0.1.0/24`를 예로 들면 다음과 같다.

| 구분 | 주소 |
|------|------|
| 네트워크 주소 | `10.0.1.0` |
| 주소 범위 | `10.0.1.0` ~ `10.0.1.255` |
| 브로드캐스트 주소 | `10.0.1.255` |
| 일반 네트워크의 호스트 주소 | `10.0.1.1` ~ `10.0.1.254` |

일반적인 `/24` 네트워크에서는 네트워크 주소와 브로드캐스트 주소를 제외한 254개를 호스트에 할당할 수 있다. 다만 AWS VPC의 Subnet에는 별도의 예약 규칙이 적용된다.

## AWS Subnet의 예약 주소

AWS는 각 Subnet CIDR 블록에서 처음 네 개와 마지막 한 개, 총 5개의 IPv4 주소를 예약한다. 이 주소들은 EC2 같은 리소스에 할당할 수 없다.

이 프로젝트의 `10.0.1.0/24`에서는 다음 주소가 예약된다.

| 주소 | AWS에서의 용도 |
|------|----------------|
| `10.0.1.0` | 네트워크 주소 |
| `10.0.1.1` | VPC 라우터 |
| `10.0.1.2` | DNS 서버 |
| `10.0.1.3` | 향후 사용을 위해 예약 |
| `10.0.1.255` | 네트워크 브로드캐스트 주소(브로드캐스트는 VPC에서 지원하지 않음) |

따라서 AWS의 `10.0.1.0/24` Subnet에서 리소스에 할당할 수 있는 주소는 `10.0.1.4`부터 `10.0.1.254`까지 총 251개다.

```text
AWS Subnet에서 사용 가능한 IPv4 주소 수 = 전체 주소 수 - 5
```

## 이 프로젝트의 CIDR 구성

```text
VPC: 10.0.0.0/16
└── Public Subnet: 10.0.1.0/24
```

`10.0.0.0/16` VPC의 범위는 `10.0.0.0`부터 `10.0.255.255`까지다. Public Subnet의 `10.0.1.0/24`는 `10.0.1.0`부터 `10.0.1.255`까지이므로 VPC 범위 안에 완전히 포함된다.

| 설정 위치 | CIDR | 의미 |
|-----------|------|------|
| VPC | `10.0.0.0/16` | 프로젝트 전체 사설 네트워크 범위 |
| Public Subnet | `10.0.1.0/24` | EC2를 배치하는 VPC 내부의 하위 네트워크 |
| Route Table | `0.0.0.0/0` | 더 구체적인 경로가 없는 모든 IPv4 트래픽의 목적지 |
| HTTP Security Group | `0.0.0.0/0` | 모든 IPv4 주소에서 오는 HTTP 요청 허용 |
| SSH Security Group | `운영자 공인 IP/32` | 운영자의 단일 IPv4 주소에서 오는 SSH 요청만 허용 |

같은 CIDR도 설정 위치에 따라 역할이 달라진다. Route Table의 CIDR은 트래픽을 **어디로 보낼지** 결정하고, Security Group의 CIDR은 트래픽을 **어디에서 허용할지** 결정한다.

### `0.0.0.0/0`

접두사 길이가 `0`이므로 네트워크 부분을 고정하지 않는다. 따라서 모든 IPv4 주소와 일치한다.

- Route Table의 `0.0.0.0/0 → Internet Gateway`는 VPC 내부 경로보다 더 구체적인 경로가 없는 트래픽을 인터넷으로 보낸다.
- HTTP 인바운드 규칙의 `0.0.0.0/0`은 모든 IPv4 주소의 접속을 허용한다.
- SSH까지 `0.0.0.0/0`으로 허용하면 인터넷 전체에 관리 포트를 노출하므로 사용하지 않는다.

### `운영자 공인 IP/32`

`/32`는 호스트 부분이 없으며 단 하나의 IPv4 주소만 나타낸다. 예를 들어 운영자의 공인 IP가 `203.0.113.10`이면 `203.0.113.10/32`로 지정하여 그 주소에서 오는 SSH 접속만 허용할 수 있다.

운영자의 공인 IP가 변경되면 기존 `/32` 규칙과 일치하지 않으므로 Security Group의 SSH 허용 CIDR도 새 주소로 갱신해야 한다.

## CIDR 포함 관계와 중복

Subnet CIDR은 반드시 VPC CIDR 안에 포함되어야 한다. 또한 같은 VPC의 Subnet끼리는 주소 범위가 겹치면 안 된다.

```text
VPC 10.0.0.0/16

10.0.1.0/24  → VPC에 포함됨
10.0.2.0/24  → VPC에 포함되고 기존 Subnet과 겹치지 않음
10.0.1.0/25  → VPC에는 포함되지만 10.0.1.0/24와 겹침
10.1.0.0/24  → VPC 범위를 벗어남
```

향후 Subnet을 추가할 때는 필요한 리소스 수와 AWS 예약 주소 5개를 고려해 크기를 정하고, 기존 Subnet 및 연결할 다른 네트워크의 CIDR과 겹치지 않는지 확인해야 한다. VPC Peering, VPN 또는 Transit Gateway로 다른 네트워크와 연결할 계획이 있다면 상대 네트워크와의 중복도 피해야 한다.

## 설계 시 확인 사항

- VPC CIDR은 필요한 모든 Subnet을 포함할 만큼 충분히 큰가?
- 각 Subnet CIDR이 VPC CIDR 안에 완전히 포함되는가?
- Subnet끼리 CIDR 범위가 겹치지 않는가?
- AWS가 예약하는 5개 주소를 제외해도 필요한 리소스를 수용할 수 있는가?
- Route Table에서 `0.0.0.0/0`의 대상이 의도한 Internet Gateway 또는 NAT Gateway인가?
- Security Group에서 전체 공개가 필요한 포트만 `0.0.0.0/0`으로 허용했는가?
- SSH 같은 관리 포트는 신뢰할 수 있는 단일 주소(`/32`) 또는 제한된 대역만 허용했는가?

이 프로젝트에서는 VPC에 `/16`, Public Subnet에 `/24`를 사용하여 주소 공간을 계층적으로 나눴고, HTTP는 모든 IPv4 주소에 공개하되 SSH는 운영자의 단일 공인 IPv4 주소로 제한했다.
